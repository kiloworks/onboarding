# Code signing policy — 코드 서명 도입 계획

현재 상태: 2026-10-19 SignPath Foundation 신청서를 제출했고, 접수 완료 화면을 확인했다. 심사 결과와 서비스 설정 안내를 기다리고 있으며 v0.2.0은 미서명이다. 이 문서는 도입 계획이며 서명 제공을 보증하지 않는다. 관리자 작업의 Rust 재구현은 기능·호환성 개선을 검증하기 전까지 보류한다.

## 발급 경로

무료 OSS용 [SignPath Foundation](https://signpath.org/apply)을 우선 검토한다. MIT 공개 저장소, 이미 배포한 설치파일, 시스템 변경과 제거 방법 문서가 있다. 신규 프로젝트의 평판, MSVC 재배포 DLL의 시스템 라이브러리 예외, 원격 관리 기능과 현재 Defender 탐지 사례는 심사에서 확인해야 한다. 승인될 것으로 가정하지 않는다.

신청에는 프로젝트 URL, 담당자 연락처, 실제 유지관리자·검토자·릴리스 승인자와 MFA 사용 여부가 필요하다. 담당자·법적 신원을 GitHub 자동화 계정으로 임의 대체하지 않는다. Foundation 인증서를 사용하면 발행자 명의는 SignPath Foundation이다. 승인 전에는 서명 후원 문구를 완료 사실로 표시하지 않는다.

유료 대안은 [Azure Artifact Signing](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)이다. 현재 공개 신뢰 조직 인증은 한국을 지원하며 개인 개발자는 미국·캐나다로 제한된다. 한국 사업자·조직의 적격 여부는 실제 신원 심사로 결정된다. 구독·실명 인증·비용 승인을 확보한 뒤 선택한다.

## 파이프라인에 적용할 순서

1. 현재와 같은 고정 소스·의존성으로 x64와 ARM64를 빌드하고 기존 테스트를 통과시킨다.
2. 자체 `onboarding.exe`에 제품명·버전 리소스를 넣고 승인된 서명 서비스로 Authenticode 서명한다. Microsoft가 발행한 CRT DLL은 자체 인증서로 다시 서명하지 않는다.
3. 서명한 앱으로 NSIS 설치파일을 만든다. NSIS 생성 제거 프로그램도 별도 서명 경로가 필요하므로 공급자와 승인·빌드 출처 검증 방식을 확정한다. NSIS 컨테이너의 내부 파일 서명을 서비스가 자동 지원한다고 가정하지 않는다.
4. 최종 설치파일을 서명하고 타임스탬프를 적용한다. 신뢰된 main/릴리스 빌드만 서명 요청을 만들고, SignPath Foundation 사용 시 릴리스마다 사람이 승인한다. 외부 PR은 서명 권한을 갖지 않는다.
5. 다운로드한 최종 설치파일, 설치한 앱과 제거 프로그램의 서명 유효성과 예상 발행자를 확인하고 기존 Windows 3종 설치·실행·제거 검사를 수행한다.
6. 서명 이후 최종 바이트로 SHA-256을 다시 생성하고 그 파일만 릴리스한다. 서명 후 바이너리를 변경하지 않는다.

서비스·조직 ID·서명 정책이 준비되기 전에는 작동하지 않는 CI 서명 단계를 추가하지 않는다. 서명 실패를 미서명 배포로 조용히 대체하지 않는다. 실제 전환 시 서명된 결과를 검사하는 릴리스 필수 조건을 함께 구현한다.

## 개인정보와 승인

소스 변경·리뷰·서명 승인은 실제 책임자를 지정해야 한다. 현재 GitHub 유지관리 계정은 kiloworks이며, 인간 서명 승인자는 신청 단계에서 확정한다. 앱은 사용자가 요청한 Tailscale 연결과 소프트웨어 다운로드에 네트워크를 사용하며 별도 분석 텔레메트리를 보내지 않는다. 연결 서비스에는 [Tailscale 개인정보 정책](https://tailscale.com/privacy-policy)이 적용된다. 시스템 변경과 원격 관리 해제는 [운영 문서](operations.md)를 따른다.

## 한계

서명은 발행자와 무결성 확인 수단이며 Defender 오탐 해제나 SmartScreen 경고 제거를 보증하지 않는다. v0.2.0의 `Trojan:Win32/Wacatac.B!ml` 분석 요청은 [재심 준비 문서](defender-submission.md)로 별도 추적한다.
